# Deploying

| Piece | Service |
|---|---|
| Database | Supabase Postgres |
| ID documents (PAN, Aadhaar, selfie) | Supabase Storage, private bucket |
| Google sign-in | Firebase |
| App (website + blockchain watcher) | Render: **staging** (from the `staging` branch, Test mode) and **live** (from `main`, Live mode) |

Netlify won't work: it can't run the blockchain watcher, which must run all the time.

---

## 1. Supabase (about 10 min)
1. supabase.com → **New project** → region **South Asia (Mumbai)**. Save the database password.
2. **Database link:** click **Connect** (top bar) → **Session pooler** → copy the string. Replace `[YOUR-PASSWORD]` and add this to the end:
   `?sslmode=require&connection_limit=5`
   This is your `DATABASE_URL`. If the password has `@ # / ?` in it, change the password to letters and numbers.
3. **Storage:** Storage → **New bucket** → name `kyc` → **Public bucket OFF** → Create.
4. **Keys:** Project Settings → **API** → copy the **Project URL** (`SUPABASE_URL`) and the **service_role** secret (`SUPABASE_SERVICE_ROLE_KEY`).
   The service_role key can read everything. Put it only in the server settings, never in a browser, chat or git.

Tables are created automatically on first start. Every table has row-level security on, so Supabase's public API can't read them.

## 2. Firebase (about 5 min)
1. Authentication → Sign-in method → **Google → Enable**.
2. Project settings → Your apps → Web app → copy `apiKey`, `authDomain`, `projectId`, `appId`.
3. After you deploy: Authentication → Settings → **Authorized domains** → add your Render address (and later your own domain).

## 3. Staging on Render (about 10 min)
1. render.com → **New → Blueprint** → connect GitHub → pick `TheCoderAS/crptrx`. It reads `render.yaml`, which sets the branch to `staging` and `APP_MODE=TEST`.
2. Fill in the values it asks for:
   - `APP_URL`: `https://crptrx-test.onrender.com` (the name Render shows; update it if Render changes it)
   - `DATABASE_URL`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`: from step 1
   - `FIREBASE_*`: from step 2
   - `SEED_SUPER_ADMIN_EMAIL` / `SEED_SUPER_ADMIN_PASSWORD`: your admin login (10+ characters)
   - `SEED_TEST_DEPOSIT_TRON` / `SEED_TEST_DEPOSIT_BSC`: your testnet "company" wallets
   - `TRONGRID_API_KEY`: optional, free at trongrid.io
3. Deploy. When it's live: open `/admin`, log in, scan the 2FA QR code.

Plan: **Free**. It goes to sleep after 15 minutes without visits, and payments aren't checked while it sleeps (they're picked up when it wakes).
Keep it awake for free: uptimerobot.com → New monitor → HTTP(s) → `https://<your-render-address>/api/health` → every 5 minutes.
The free plan includes 750 hours a month, enough for this one service running all month. First visit after a sleep takes about a minute.
`ENCRYPTION_KEY` is generated by Render once. Don't delete or change it: that makes stored PAN, bank numbers and 2FA unreadable.

## 4. Live on Render
A second Render service, built from `main`. Every `staging` → `main` merge is a release: Render deploys it and GitHub tags it (`v1.0.0`, `v1.1.0`, …).

1. Supabase: a **new project** for live (step 1 again). Never share the staging database with real customers.
2. render.com → **New → Web Service** → this repo → branch **`main`**, runtime **Docker**, region **Singapore**, docker command `entrypoint all`, health check `/api/health`. Use a **paid plan**: the free one sleeps, and payments aren't checked while it sleeps.
3. Environment (copy from staging, then change):
   - **`APP_MODE=LIVE`**. Required: without it the app refuses to start (Render keeps the previous version running).
   - `APP_URL`: the live address; `SECURE_COOKIES=true`, `TRUSTED_PROXY_HOPS=1`
   - `DATABASE_URL`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_STORAGE_BUCKET=kyc`: from the **new** project
   - **New** `ENCRYPTION_KEY` (`openssl rand -hex 32`) and `LINK_SIGNING_SECRET`. **Save the key offline**: losing it makes PAN, bank numbers and 2FA unreadable.
   - `DEV_LOGIN_ENABLED=false`, `DEV_TOOLS_ENABLED=false` (they are forced off in Live anyway)
   - `EMAIL_PROVIDER=console`, `SMS_PROVIDER=console` until real providers are set up (then Resend / MSG91)
   - `BSC_LIVE_RPC_URL`: the free `https://bsc-rpc.publicnode.com` detects payments; a keyed provider also makes customer TxIDs and Re-check work. `TRONGRID_API_KEY` strongly advised.
   - Firebase values (same project as staging is fine), `WALLETCONNECT_PROJECT_ID`
   - `SEED_SUPER_ADMIN_EMAIL` / `SEED_SUPER_ADMIN_PASSWORD`: your first admin login; change the password and set up 2FA on first login
4. Add the live domain to Firebase **Authorized domains** and Reown's allowed domains.
5. In the live app: Settings → set Live deposit addresses and company details. Without email/SMS: turn **email sign-in off** (Google only) and **mobile number required off**.
6. Do one small real order end to end before telling customers.

Supabase backups: the free plan has none you can restore yourself. Before real money, use a paid plan with daily backups and do one test restore.

## 5. Android app (VisionPay)

The app in `android/` shows the website full screen and adds native Google sign-in, notifications, camera uploads and downloads. Screens come from the website, so website releases update the app straight away; a new app file is only needed for changes inside `android/`.

**Builds (automatic)**
- Every merge into `staging` → GitHub pre-release `vX.Y.Z-test.N` with `VisionPay-Test-vX.Y.Z-test.N.apk` ("VisionPay Test", `com.visionpay.live.app.test`, opens the staging website).
- Every merge into `main` → the `vX.Y.Z` release gets `VisionPay-vX.Y.Z.apk` ("VisionPay", `com.visionpay.live.app`, opens the live website). Same version as the release.
- Each website's `/app` page links the newest file for it, and the app offers updates by itself.

**Links open in the app (Android App Links)**
- Each website serves `/.well-known/assetlinks.json` naming its own app (live site → `com.visionpay.live.app`, staging → `com.visionpay.live.app.test`) and the signing key's SHA-256 fingerprint. With the app installed, links to the site (invite links, order links) open straight in the app; without it, in the browser.
- The fingerprint defaults to our release key. If the signing key ever changes, set `ANDROID_CERT_SHA256` on both Render services (the new fingerprint is printed on every app build as "Signing key fingerprints").
- Phones check the file when the app is installed or updated. Check one with `adb shell pm get-app-links com.visionpay.live.app` ("verified"). The emulator test in CI reports the same.

**One-time setup**
1. Signing key (on your own computer; keep the `.jks` file and passwords backed up in two places, a lost key means no more updates):
   `keytool -genkeypair -v -keystore visionpay-release.jks -alias visionpay -keyalg RSA -keysize 4096 -validity 10000`
2. GitHub → repository → Settings → Secrets and variables → Actions → **Secrets**:
   `ANDROID_KEYSTORE_BASE64` (output of `base64 -w0 visionpay-release.jks`, on macOS `base64 -i visionpay-release.jks`), `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS` (`visionpay`), `ANDROID_KEY_PASSWORD`.
3. Optional **Variables** (same page): `ANDROID_LIVE_URL`, `ANDROID_TEST_URL` when the websites move to your own domain. Changing them needs a new app file.
4. Firebase → Project settings → Your apps → **Add app → Android**, twice: `com.visionpay.live.app` and `com.visionpay.live.app.test`. In each, add the **SHA-1** fingerprint shown in the "Signing key fingerprints" note of the app build on GitHub (Actions → Android app / Release). No need to download `google-services.json`.
5. Render, staging service: `GOOGLE_WEB_CLIENT_ID` (Google Cloud → APIs & Services → Credentials → "Web client (auto created by Google Service)" → Client ID) and `FIREBASE_ANDROID_APP_ID` (the test app's App ID, `1:…:android:…`). Live service: the same client ID and the live app's App ID. `FIREBASE_MESSAGING_SENDER_ID` must be set too (Project settings → Cloud Messaging → Sender ID).
